From Review #1

Ponytail, by Dietrich Gebert · Reviewed November 2026 · Done free, as a demonstration

Grade: A-

Ponytail is a mode for coding agents: a six-rung ladder that asks, before any code is written, whether the thing needs to exist at all. Its current headline numbers are:

  • Less code than no skill−53%
  • Less time−41%
  • Lower cost−26%
  • Fewer tokens−45%
  • Risky logic that ships with a test98%, vs 68% without

Those numbers rest on a 39-task benchmark, 5 runs per arm, 585 sessions, reported with 95% bootstrap intervals — and the repo itself corrects the older “80 to 94%” figure that made the skill known. That correction is in the benchmark file, dated 2026-06-18, crediting the issue that raised it.

The main finding: the skill collides with its own sibling. The main skill's description claims “reviewing” as a trigger; the bundled ponytail-review skill claims “review this”, “code review”, and “review my PR”. The plugin installs both by default, so one review request matches two skills with different output contracts.

How an audit runs

Four steps. One person, start to finish.

The person who reads your skill writes your report. There is no handoff and no summary of a summary.

  1. List

    Every claim, instruction, and rule is written into a list before any judgment. If it is not on the list, it is not assumed. If it is on the list, it gets checked.

  2. Check

    Each item is tested against the source: the skill's own files and observed behavior, or the live data source. Findings name the file, line, or document they came from.

  3. Push on it

    Instructions and sources are tried past the easy case — unclear inputs, rules that conflict, content from outside, copies that are out of date — to find where an agent goes wrong in normal use, not in a demo.

  4. Report and grade

    Findings are written in plain language, ordered by how much they matter, and rolled into one grade: a letter, in the text of the report.

Review #1, in full

Skill Audit — completed review

Skill Audit: Ponytail by Dietrich Gebert

A session-persistent mode for coding agents. Once active, every coding task runs through a six-rung ladder in skills/ponytail/SKILL.md — does it need to exist, is it already in this codebase, does the standard library or platform do it, is a dependency already installed, can it be one line, only then the minimum code that works — at three intensity levels (lite, full, ultra). Around that core sit sibling skills for diff review (ponytail-review), whole-repo audit (ponytail-audit), and a ledger of deferred shortcuts (ponytail-debt), plus adapters for roughly twenty agent hosts.

Demonstration review — done free. No fee was charged. Paid audits are graded on the same standard.

Claims check

The current headline is:

  • Code−53%
  • Time−41%
  • Cost−26%
  • Tokens−45%
  • Risky logic that ships with a test98%, vs 68% without the skill

The supporting file, benchmarks/results/2026-10-07-agentic.md, is unusually solid for this category: 39 tasks, 5 runs per arm, 585 sessions, medians per task, geometric means with 95% bootstrap intervals, a full per-task table, and a user-runnable harness. It is also candid about its limits: 21 of the 39 tasks measure size only, a completeness-judge miscount is explained rather than buried, and where the skill did not win the result is reported as not significant.

Qualifications a reader should keep. All headline numbers come from one model (Opus 5.5) in one harness (Claude Code), run by the author; the shipped harness makes replication possible but not independent. The repo links two genuinely independent benchmarks in benchmarks/README.md, and one (KuldeepB19, 24 tasks) found Ponytail “trims everyday bad-input handling on 5 of 24 tasks,” a caveat hosted on the project's own page. Cost is the weakest claim: cheaper on 30 of 38 tasks, not all of them.

On the famous original number: the 80 to 94% figure came from the June 2026 single-shot benchmark and counted the baseline model's prose as code. The repo does not hide this: benchmarks/README.md carries a dated note (“Read this number honestly,” updated 2026-06-18) crediting the GitHub issue that called it out, and replaces it with the agentic result. What could not be verified from the repo alone: whether results hold on other models or hosts (the instruction-only adapters are unbenchmarked), and the raw blind-judge judgments behind the reply-preference scores.

Quality findings

  1. Trigger overlap with its own sibling. The main skill's description claims “reviewing” among its coding tasks; skills/ponytail-review/SKILL.md claims “review this”, “code review”, and “review my PR”. Install both, as the plugin does by default, and a review request matches two skills with different output contracts.
  2. The ladder has already drifted across surfaces. SKILL.md rung 3 merges “standard library or a platform feature” into one step; the README's “How it works” graphic shows seven rungs with those separate, plus a test rung the prompt states separately. With AGENTS.md as a third surface, drift is a when, not an if.
  3. The test rule's boundary is genuinely fuzzy, and the benchmark proves it. “Non-trivial logic (a branch, a loop, a parser, money or security…)” reads crisply, but the benchmark team had to pre-sort tasks into needs-test, does-not, and borderline, excluding 6 borderline tasks from the test metric. Users will hit the same ambiguity the measurers did.
  4. A strength worth naming: the requirement to end every reply with what was skipped or not checked. The benchmark's blind judge preferred Ponytail 5 replies over v4.13 mainly for exactly that ending. It is the rare prompt feature with measured evidence behind it.

Safety findings

The obvious fear with a “write less” skill is that the savings come out of validation, error handling, and tests. Ponytail defends against this in writing: SKILL.md carries an explicit never-cut list (“validation at trust boundaries, error handling that prevents data loss, security, accessibility, the calibration real hardware needs, anything the user asked for”), moved or merged code “keeps its error handling and validation”, and the test rule makes a check a condition of done. The benchmark's safety tier backs the text: six security tasks (SQL injection, path traversal, forged tokens, rate limiting, malformed CSV, caching), all 30 runs passed in every arm, and hidden-check pass rates level with no skill (96.7% vs 95.6%).

Three residual risks. First, placement: the never-cut list sits at the end of the prompt, after six rungs of cut pressure; a gate placed after the decision it constrains is weaker than one placed before it. Second, error handling is protected only where it “prevents data loss”; error handling kept for debuggability is exactly what a lazy pass trims, a risk the linked independent benchmark's bad-input-handling finding hints at. Third, test depth: in cells where a test exists, Ponytail's tests caught 69% of injected bugs, slightly below no-skill's 77%. The skill reliably produces a test; it is a little thinner than the one an unhurried agent writes.

Verdict

Grade: A-

Ponytail is the rare viral skill that survives its own audit. The prompt is short, specific, and honest about its priorities; the guardrails are written down where a reviewer can check them; and the benchmark file is more transparent about methodology and failure than most published evaluations, including a public correction of the inflated number that made it famous. The deductions are real but fixable: a self-inflicted trigger collision, a ladder already drifting across its own surfaces, and safety rules that sit one paragraph too late.

Three fixes, in priority order

  1. Resolve the review trigger collision. Remove “reviewing” from the main skill's description, or state that review requests route to ponytail-review. One request should never match two of your own skills.
  2. Move the never-cut list above the ladder, as a gate the rungs are read through, and widen the error-handling clause beyond data loss to cover error handling kept for diagnosis. The rule is good; its position and scope undersell it.
  3. Pin the ladder to one canonical text. Generate or CI-check the README ladder and compact AGENTS.md against SKILL.md, and label headline numbers with their scope (“Opus 5.5, Claude Code, author-run”) wherever they appear. They are strong enough to carry their caveats.
